The short version

Devin writes the fix. A separate checker Devin can't touch proves it works. A human only adds a label and reviews the PR.

01 / What

A bug report goes in. A proven fix comes out.

The problem. Every team has a backlog of small, well-defined bugs: tests too weak to catch regressions, APIs that crash on bad input, scanner findings. Each is real risk, but no one has time for them. And when an AI writes the fix, a reviewer still has to work out whether it actually works, so the time saved goes back into checking.

Why it matters. Senior engineers spend review time on low-value fixes, and unproven AI PRs pile up or get merged on trust.

The fix. Devin writes the fix. Then a checker Devin can't touch proves it really works, before any human spends time on it. Live runs on our Superset fork covered weak tests that missed real bugs and an API that crashed on bad input.

02 / How

One label starts it. Four Devin APIs do the work.

  • An engineer tags the issue devin-remediate. GitHub sends a signed message; we check it came from our repo and the issue is approved, then save one job that survives a restart.
  • Playbook = the team handbook: reproduce first, smallest fix, allowed files only, never touch the checker, never merge.
  • Knowledge = the project brief: branch, files, what "broken" looks like. Both set up once and fingerprinted, so a changed copy is rejected.
  • Attachments hand Devin the evidence for each bug. Sessions start the work with a budget cap and check in until the PR is ready.
  • If our app crashes, it finds the session again. If the fix is wrong, Devin gets one correction.
  • One comment on the issue (and the PR) updates itself: working, PR opened, checking, verified.
  • Behind the scenes: every job page links its Devin session, so you can watch Devin read the code, reproduce the bug, fix it, and open the PR. The key design choices are listed below.
03 / Why Devin

Only an autonomous agent can do the middle part.

Without one, this is not practical: every bug would need either an engineer at the keyboard or custom code written per bug. The whole point is that no one does either.

  • A script or codemod can't do this: each bug needs someone to read the code, reproduce it, choose the fix, and write the test. Devin does that with no per-bug code.
  • A copilot needs an engineer driving every step. Devin is called from an API: an event fires and a PR comes back while no one is watching.
  • Devin works in its own machine and opens its own PR, so many sessions can run side by side and the backlog shrinks without taking engineer time.
  • Devin's API gives us what we would otherwise build: budget caps, session tags for crash recovery, follow-up messages for one correction, and Playbooks and Knowledge for team rules.
  • The independent checker is what makes that autonomy safe to hand over.
04 / Why trust it

Devin can't grade its own homework.

  • The checker lives outside Devin's reach and tests the exact commit Devin pushed.
  • Good inputs must still work; every bad input must be rejected. A partial fix fails.
  • For weak tests, we plant a known bug: the old test misses it, the new test must catch it.
  • We confirm each bug reproduces before spending anything. A broken checker is never counted as a pass.
  • Leaders count proven fixes, not PRs opened: time from label to proof, first-try rate, one label and one review per fix. Cost shows only when Devin reports it; never guessed.
05 / When

Use it for bugs a computer can check.

  • Good fit: weak tests, crashes on bad input, security scanner findings.
  • New bug type = one config entry + one checker.
  • Not for fuzzy feature work. It never merges on its own.
  • For production: isolated machines, a login, a real job queue.

In a real customer engagement

  • Week 1: plug in the customer's scanner or Jira feed as the trigger.
  • Pilot: 10 to 20 approved cases, with success targets agreed with the team (proven-fix rate, time to proof, review time).
  • Then: grow the case library, run sessions in parallel, and track provider-reported cost per proven fix.

02 / How: key architectural decisions

Seven choices that make it safe to run unattended.

  1. Allow-list, not free text. Only issues bound to an entry in cases.yaml start work; the webhook signature is checked with HMAC and unapproved issues get a 422. app/main.py app/cases.py
  2. Durable job before any paid call. One SQLite row per issue, written under a lock so GitHub redeliveries reuse the job instead of paying twice. Status moves only along an approved state machine. app/db.py app/models.py
  3. Crash-safe Devin sessions. Each session is tagged with its job id; if the app dies mid-create, it finds the session again by tag instead of starting a new one. Budget cap per session; at most one correction message in the same session. app/devin.py app/orchestrator.py
  4. Team rules as versioned config. Playbook and Knowledge are created once per repo and named by a content hash, so a changed copy gets a new name and is never silently reused. app/devin.py
  5. Separate trust plane. The validator fetches the PR head, checks out that exact commit in a throwaway worktree, rejects edits outside the allowed files, strips secrets from the environment, and runs a checker Devin can't edit. Only the validator can say VERIFIED; a broken checker is INFRA_ERROR, never a pass. app/validator.py
  6. Evidence-first observability. Every step is an event; metrics, the dashboard, and /report.json are computed from that log. The GitHub status comment is edited in place via a hidden marker, so there is one card, not a stream. app/report.py app/metrics.py app/issue_status.py
  7. Credential-free simulation. The same webhook, database, and orchestrator run with fake providers for demos, and simulated runs are never mixed into live metrics. app/simulation.py
