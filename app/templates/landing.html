{# ELI5: the plain-language version of the Loom story, in What, How, Why, When order. #}

The short version

Devin writes the fix. A separate checker Devin can't touch proves it works. A human only adds a label and reviews the PR.

01 / What

A bug report goes in. A proven fix comes out.

Devin writes the fix. Then a checker Devin can't touch proves it really works, before any human spends time on it. Live runs on our Superset fork covered weak tests that missed real bugs and an API that crashed on bad input.

02 / How

One label starts it. Four Devin APIs do the work.

  • An engineer tags the issue devin-remediate. GitHub sends a signed message; we check it came from our repo and the issue is approved, then save one job that survives a restart.
  • Playbook = the team handbook: reproduce first, smallest fix, allowed files only, never touch the checker, never merge.
  • Knowledge = the project brief: branch, files, what "broken" looks like. Both set up once and fingerprinted, so a changed copy is rejected.
  • Attachments hand Devin the evidence for each bug. Sessions start the work with a budget cap and check in until the PR is ready.
  • If our app crashes, it finds the session again. If the fix is wrong, Devin gets one correction.
  • One comment on the issue (and the PR) updates itself: working, PR opened, checking, verified.
03 / Why trust it

Devin can't grade its own homework.

  • The checker lives outside Devin's reach and tests the exact commit Devin pushed.
  • Good inputs must still work; every bad input must be rejected. A partial fix fails.
  • For weak tests, we plant a known bug: the old test misses it, the new test must catch it.
  • We confirm each bug reproduces before spending anything. A broken checker is never counted as a pass.
  • Leaders count proven fixes, not PRs opened: time from label to proof, first-try rate, one label and one review per fix. Cost shows only when Devin reports it; never guessed.
04 / When

Use it for bugs a computer can check.

  • Good fit: weak tests, crashes on bad input, security scanner findings.
  • New bug type = one config entry + one checker.
  • Not for fuzzy feature work. It never merges on its own.
  • For production: isolated machines, a login, a real job queue.
